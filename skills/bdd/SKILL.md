# BDD From User Input

将用户在对话中提供的需求描述转换为可执行导向的 Gherkin `.feature` 文件，按命令组织，每个命令产出一份。BDD 直接从用户输入推导命令、参与者、业务规则与查询展示场景，并将命令的写操作链路实例化为主路径与关键失败分支的行为场景（Given/When/Then）。

## 职责边界

- 直接基于用户在对话中提供的需求描述生成，不依赖 PRD、UI-SPEC、事件风暴 `model_only.json`、上下文术语文件，也不依赖触发层设计文档。
- 命令、参与者、业务规则、查询展示场景均由 AI 从用户输入推导；遇信息不足或歧义时停下向用户确认，禁止自行检索仓库补全。
- 按命令组织：用户输入中推导出的每个写操作命令产出一份独立的 `.feature`。
- 查询展示补充：BDD 必须主动推导每个功能模块所需的页面查询场景（列表、详情、子表），确保数据展示有行为规格覆盖。
- 新增表单补充：含新增表单录入的命令（创建/新增类）必须生成"表单字段展示"场景（定义字段名、字段展示形式、是否存在必填 * 号）与按字段维度的校验场景大纲，确保每个表单字段的展示与校验规则都有行为规格覆盖。

## Hard Gate（强门禁）

- 先检查输入是否齐全，再做任何生成动作。
- 输入缺失或不足以推导命令时立即停止，禁止继续。
- 任何情况下禁止自行检索仓库（禁止 `glob`/`grep`/`read`/shell 搜索）替代用户输入。
- 输入不足时，只允许输出"缺失项清单 + 需要用户补充的内容格式"。

必需输入：
- `bounded_context`：用户显式提供。
- 功能需求描述：用户在对话中提供的需求文字（功能、操作、参与者、业务规则、页面/查询需求等），需足以推导出至少 1 个写操作命令。

## Quick start

1. 校验是否收到 `bounded_context` 与足以推导命令的功能需求描述；不足则按"输入缺失固定回复"提示用户并停止。
2. 以用户输入中的领域术语为准，统一词汇，不自造同义词。
3. 从用户输入推导"命令清单"（写操作）、"参与者清单"及每个命令的业务规则。
4. 执行"功能模块划分"，将命令分配到内聚的功能模块。
5. 执行"查询展示场景补充"，为每个功能模块推导页面查询 `.feature`。
6. 执行"新增表单场景补充"（见 Workflow 第 3.7 步），为含新增表单的命令推导表单字段展示场景与字段维度校验场景大纲。
7. 复用 `gherkin` skill 的写作规范，为每个命令和查询场景各生成一份 `.feature`。
8. 输出：`docs/user-story/<bounded_context>/<feature>/<场景名>.feature`。

## Workflows

### 1) 输入门禁检查

- [ ] 已收到用户显式提供的 `bounded_context`
- [ ] 已收到功能需求描述，且能推导出至少 1 个写操作命令
- [ ] 若任一项不满足，停止并提示，不做任何仓库检索

### 1.1) 输入缺失固定回复

```md
缺少必要输入，暂不能生成 BDD `.feature` 文件。

请补充：
1. 限界上下文：`bounded_context`（需显式提供）
2. 功能需求描述：功能、操作、参与者、业务规则、页面/查询需求等（需足以推导出至少一个写操作命令）

收到以上输入后，我将按命令生成并写入：`docs/user-story/<bounded_context>/<feature>/<命令名>.feature`。
```

### 2) 术语对齐

- 以用户输入中的领域词汇为准，不自造同义词。
- 遇术语歧义或一词多义时，向用户确认后再继续，不得自行裁定。
- 完成标志：能为每个命令列出至少一条可溯源的业务规则依据。

### 3) 命令与业务规则推导

用户输入不提供结构化的命令/事件清单，AI 必须从用户输入推导每个写操作命令及其业务规则：

- 命令推导：从用户输入的功能描述、用户操作、状态流转中识别写操作（如创建、上架、下架、导入、领取等），每个写操作为一个命令。
- 参与者推导：从用户输入中识别每个命令的发起者（用户角色或系统自动触发）。
- 业务规则推导来源（按优先级）：
  1. 用户输入中明确描述的校验、约束、前置条件。
  2. 命令操作语义蕴含的隐含规则（如"上架活动"蕴含"活动必须处于未上架状态"）。
- 推导约束：
  - 每条规则必须可溯源到上述来源之一，禁止凭空臆造。
  - 若某命令无法从用户输入推导出任何失败分支，只生成主路径场景，不强行编造失败场景。
  - 推导结果以"命令 -> 规则列表"形式组织。
- 完成标志：每个命令至少有一条主路径规则；关键命令（涉及状态变更、金额、权限）至少有一条失败分支规则。

### 3.5) 功能模块划分

`<feature>` 目录代表一个具体的功能模块。AI 必须将命令按功能内聚性分配到不同模块。

- 划分原则：
  1. **状态流转内聚**：围绕同一聚合根状态机流转的命令归为一组（如创建->上架->下架->自动结束）。
  2. **职责单一**：独立职责的命令单独成模块（如名单导入、时间调整）。
  3. **参与者/触发方式差异**：用户侧操作与系统侧自动任务若职责不同，应分属不同模块。
  4. **粒度适中**：每个模块包含 1-5 个命令；若所有命令语义高度一致（如仅 2-3 个命令且围绕同一操作），可合并为一个模块。
- 命名规则：`<feature>` 使用"领域名词 + 管理/操作"形式（如"活动生命周期管理""活动积分管理"），避免与功能名称完全重复。
- 完成标志：每个命令被且仅被分配到一个模块；模块命名与命令集合语义一致。

### 3.6) 查询展示场景补充

用户输入常聚焦写操作，读模型查询场景需由 AI 主动推导。AI 必须从用户体验角度推导每个功能模块所需的页面查询场景，并生成对应的 `.feature` 文件。

- 推导轴一：模块页面推导（按功能模块逐一审视，来源优先用户输入中提到的页面/查询需求）
  1. **列表页**：每个功能模块是否需要一个列表视图？列表项应展示哪些关键字段让运营人员快速掌握全局？需要哪些筛选、搜索、排序能力？
  2. **详情页**：是否需要一个详情视图？详情应划分哪些信息区域（基本信息、规则配置、统计数据）？每个区域展示哪些字段？
  3. **子表/明细页**：是否存在需要独立查看的从属数据（如名单成员、积分记录）？每条记录展示哪些字段？是否需要筛选和分页？
  4. **空态与异常**：无数据时展示什么提示？访问不存在的资源时如何反馈？
- 推导轴二：写操作->读模型投影推导（按用户输入中每个写操作命令逐条追踪）
  1. 遍历推导出的每个命令，追问：该操作完成后，是否会创建或更新下游读模型记录？（如"活动积分已领取"-> 积分变动明细记录被写入）
  2. 若存在投影记录，继续追问：用户或运营人员是否需要查询这些记录？查询入口在哪个页面？展示哪些字段？
  3. 对需要查询的投影记录，生成对应的查询 `.feature`，归入触发该操作的功能模块目录。
  4. 跨聚合投影（如 campaign 操作投影到 point-wallet 的积分变动明细）仍归入触发侧模块，因为查询场景的业务语境由触发侧决定。
- 字段设计原则：
  - 列表页字段精简，只放"扫一眼就能决策"的关键指标（如状态、进度、时间）。
  - 详情页字段完整，覆盖配置信息 + 运行统计。
  - 子表字段聚焦单条记录的跟踪要素（如谁、什么状态、什么时间）。
  - 统计汇总（如总量、已使用、已过期）放在明细页顶部，提供全局视角。
- 命名规则：查询 feature 文件名以"查询"开头 + 数据对象（如"查询活动列表""查询活动名单"）。
- 完成标志：每个功能模块至少有一份查询 `.feature`（列表或详情），覆盖主路径 + 筛选 + 空态。

### 3.7) 新增表单场景补充

当命令语义包含新增表单录入时（命令名含"创建""新增""添加"等，或命令需要用户填写多字段表单后提交），必须在该命令的 `.feature` 中补充两类表单场景。

- 场景类型一：表单字段展示场景（每个表单 1 个）
    1. 目的：定义表单的字段名、字段展示形式（控件形态）与是否存在必填 * 号。
    2. 字段清单来源（按优先级）：PRD 中明确定义的表单字段；命令-事件语义蕴含的必要字段（如"创建活动"蕴含活动名称、活动时间）。
    3. 每个字段必须明确三要素：字段名（与 UI 标签一致）、展示形式（控件形态，见第 5 节"表单场景写作规范"）、是否必填（必填字段在展示断言中带"必填*号"）。
    4. 字段清单同时以"表单字段规格表"注释块落盘，格式遵循 `../gherkin/references/form-specification.md`。
- 场景类型二：字段维度校验场景大纲（每个有校验规则的字段 1 个）
    1. 目的：以字段为维度分别校验每个字段的规则；被测字段是唯一变量，其他必填字段均预填有效值。
    2. Examples 必须逐条覆盖该字段的校验规则：必填空值、边界值（最小/最大长度、数值范围）、格式非法值等。
    3. 必填字段至少覆盖空值一行；无任何校验规则的非必填字段可不单独建大纲。
    4. 跨字段规则（比较关系、依赖关系、唯一性）不归入字段维度大纲，使用独立场景表达，遵循 `../gherkin/references/form-specification.md`。
- 完成标志：每个含新增表单的命令有 1 个字段展示场景；每个有校验规则的字段有 1 个字段维度场景大纲，且 Examples 行数不少于该字段的规则条数。

- 写作与校验遵循：
  - `../gherkin/SKILL.md`
  - `../gherkin/references/gherkin-syntax.md`
  - `../gherkin/references/best-practices.md`

  - `../gherkin/references/form-specification.md`（表单字段规格表、标准控件类型与统一提示语规范）

### 5) 写作规范

#### Feature 功能描述：用户故事

每份 `.feature` 文件头部的功能描述（`Feature:` 下方的描述文本）必须遵循用户故事标准写法：

```gherkin
Feature: <命令名>
  作为 <参与者角色>，
  我希望 <执行该命令/完成该操作>，
  以便 <获得的业务价值>。
```

- 参与者角色取用户输入中描述的该命令发起者/参与者。
- 业务价值从用户输入中提取；若用户输入未明确，从命令操作语义推导。
- 一个命令对应一个用户故事，不合并多个命令。

#### 业务规则：SBVR 规范

`.feature` 中涉及的业务规则必须直接作为 Gherkin `Rule`（中文关键词 `规则:`）的标题，使用 SBVR（Semantics of Business Vocabulary and Business Rules）标准陈述句写法，不以 `#` 注释另行标注：

```gherkin
规则: <SBVR 陈述句>
  场景: <场景名>
    假设 ...
    当 ...
    那么 ...
```

- 结构规则（约束/不变量）：
  - `规则: 每个 <实体> 必须 <约束条件>`
  - 例：`规则: 每个活动必须处于"未上架"状态才能执行上架`
- 必要性规则：
  - `规则: 必须满足 <条件> 才允许 <操作>`
  - 例：`规则: 必须满足活动名单已导入才允许上架活动`
- 禁止性规则：
  - `规则: 禁止 <被禁止的行为>`
  - 例：`规则: 禁止对已结束的活动执行时间修改`
- 推导性规则（计算/派生）：
  - `规则: <实体> 的 <属性> 由 <计算方式> 确定`

SBVR 写法约束：
- 每条规则是完整的陈述句。
- 使用领域术语（与用户输入一致），不使用技术实现词汇。
- 一条规则只表达一个约束，不复合。
- 一条 SBVR 规则对应一个 `规则:` 块，该规则约束的所有 Scenario 归入此块下方。

#### 表单场景写作规范

含新增表单的命令，其 `.feature` 必须包含"表单字段展示场景"与"字段维度校验场景大纲"两类场景（由第 3.7 步推导产出）。文件头部声明 `# language: zh-CN`，场景使用中文关键字书写。

##### 表单字段展示场景

每个新增表单必须有且仅有 1 个字段展示场景，逐字段断言字段名、字段展示形式与必填 * 号：

```gherkin
场景: 注册表单展示所有字段
  假设 我打开了注册页面
  那么 我应该看到"用户名"输入框，带必填*号
  并且 我应该看到"邮箱"输入框
  并且 我应该看到"密码"输入框，带必填*号
  并且 我应该看到"确认密码"输入框，带必填*号
```

写法约束：
- 场景名固定格式：`<表单名>表单展示所有字段`。
- 每个字段占一行断言：`我应该看到"<字段名>"<控件形态>`；必填字段追加 `，带必填*号`，非必填字段不追加。
- 控件形态由表单字段规格表中的控件类型映射而来：文本输入/多行文本→输入框、数字输入→数字输入框、下拉选择→下拉框、多选→多选框组、单选→单选框组、日期选择器→日期选择器、时间选择器→时间选择器、日期时间选择器→日期时间选择器、开关→开关、文件上传→上传按钮、级联选择→级联选择器、树选择→树选择器、自动补全→搜索选择框。
- 断言顺序与表单字段规格表中的字段顺序一致。

##### 字段维度校验场景大纲

每个有校验规则的字段必须有 1 个场景大纲，以字段为维度单独校验该字段的规则；被测字段是唯一变量：

```gherkin
# 用户名字段（按字段维度）
场景大纲: 用户名字段校验
  假设 我在注册页面
  并且 其他必填字段都填写有效值
  当 我在"用户名"输入框中输入"<输入值>"
  并且 我点击"创建账号"
  那么 我应该看到"<提示信息>"

  例子:
    | 输入值           | 提示信息                       |
    | （空）           | 用户名不能为空                 |
    | ab               | 用户名至少3个字符              |
    | 21个字符的用户名 | 用户名最多20个字符             |
    | user@name        | 用户名只能包含字母数字和下划线 |
```

写法约束：
- 大纲名固定格式：`<字段名>字段校验`；大纲上方以注释标注 `# <字段名>字段（按字段维度）`。
- Given 固定两步：`我在<表单所在页面>` + `其他必填字段都填写有效值`，保证被测字段是唯一变量。
- When 步骤引用被测字段的控件形态（输入类用 `在"<字段名>"输入框中输入"<输入值>"`，选择类用 `选择`，上传类用 `上传`）。
- 提交动作使用该表单实际的提交按钮名（如 `我点击"创建账号"`）。
- Examples 固定两列：`输入值` 与 `提示信息`；空值一律写 `（空）`。
- Examples 必须逐条覆盖该字段在第 3.7 步推导出的全部校验规则；提示信息文案以 PRD 为准，PRD 未明确时遵循 `../gherkin/references/form-specification.md` 的统一提示语规范。
- 以上示例仅示意结构与写法，实际字段、输入值与提示信息以当前命令的推导结果为准。

### 6) 规格生成规则

- 每个推导出的写操作命令生成且仅生成一份 `.feature` 文件。
- 一份 `.feature` 内可包含多个 Scenario，覆盖该命令的主路径与关键失败分支。
- 场景语义必须与第 3 步推导的命令操作链路及业务规则一致，不得臆造业务行为。
- 校验失败分支由第 3 步推导的业务规则驱动；每条失败场景的 Given 或 Then 必须能追溯到具体规则来源。
- 查询展示 `.feature` 由第 3.6 步推导产出，场景应覆盖：默认展示（含字段断言）、筛选/搜索、空态提示；详情页还应覆盖资源不存在的异常提示。
- 查询 `.feature` 的 Given 步骤应使用数据表格（Data Table）列举展示字段，使字段断言可验证。
- 含新增表单的命令，其 `.feature` 必须包含 1 个表单字段展示场景与每个有校验规则字段的字段维度场景大纲（见第 3.7 步与第 5 节"表单场景写作规范"）；这些场景写入该命令自身的 `.feature`，不单独建文件。

### 7) 输出路径与命名

- 输出目录固定：`docs/user-story/<bounded_context>/<feature>/`
- `<bounded_context>` 取自用户显式提供。
- `<feature>` 为具体功能模块名称（非整份需求的笼统归类），由第 3.5 步"功能模块划分"确定。
- 文件名固定：`<命令名>.feature`（取推导出的命令名）。
- 同一份用户输入的命令按功能模块划分到不同 `<feature>` 目录。
- 示例（功能：运营活动）：
  - 命令"创建活动" -> `docs/user-story/campaign/活动生命周期管理/创建活动.feature`
- 查询展示 `.feature` 归入对应功能模块目录，文件名以"查询"开头：
  - `docs/user-story/campaign/活动生命周期管理/查询活动列表.feature`

### 8) 交付说明

- 汇报新增/更新的 `.feature` 文件清单。
- 说明每份文件对应的命令与来源（用户输入）。
- 列出功能模块划分结果（模块名 -> 包含命令），并说明划分依据。
- 列出推导的业务规则摘要（命令 -> 规则 -> 来源），便于用户校验。
- 列出补充的查询展示场景清单（模块 -> 查询 feature -> 展示字段摘要），便于用户校验字段设计。
- 若用户输入未覆盖查询需求，说明查询场景系基于写操作推导，建议用户复核。
- 列出新增表单场景覆盖清单（命令 -> 字段展示场景 -> 字段维度大纲及字段清单），便于用户校验表单字段设计。
- 若存在输入歧义，只列歧义点并请求用户补充，不得自行推断。
