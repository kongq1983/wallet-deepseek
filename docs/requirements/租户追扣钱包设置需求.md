## 1. 背景与目标

校园消费场景下，同一位用户可能同时持有多个钱包（如工作钱包、追扣钱包）。不同机构（餐厅、档口、超市）、不同身份（学生、老师）、不同设备（消费终端）对"能用哪个钱包消费""余额不足时能否继续扣款""能否脱机消费"的要求各不相同。

本需求为学校管理员提供一整套**配置能力**：定义租户级钱包配对关系，维护机构树，为机构配置支付参数与可消费身份，登记设备，并由系统据此自动生成**设备侧可执行的钱包配置数据（下发表）**。

**目标**

1. 学校管理员可自助完成全部配置，无需开发介入。
2. 配置变更后，系统自动重算并刷新下发表，保证设备侧配置与平台配置一致。
3. 下发表保留完整变更轨迹（失效标记 + 版本号），可追溯任意历史状态。

## 2. 范围

### 2.1 范围内

| 编号 | 能力 |
| --- | --- |
| F-1 | 租户钱包设置（工作钱包 ↔ 追扣钱包 配对维护） |
| F-2 | 机构管理（树形维护） |
| F-3 | 机构支付参数配置 |
| F-4 | 身份管理 |
| F-5 | 设备管理 |
| F-6 | 下发表自动生成与查询 |

### 2.2 范围外（明确不做）

- **消费交易与扣款执行**：实际的消费、扣款、追扣动作由设备侧自行处理；平台只负责配置与下发数据。
- **追扣账务处理**：欠款形成、补扣、清偿、对账、清算一律不在本需求范围。
- **机具通信协议**：不对接设备通信协议、不实现下发通道；平台只负责**生成并保存下发表数据**。
- **外部系统集成**：不接入任何外部系统（人员主数据、财务、一卡通等），机构与身份均在平台内创建维护。
- **操作审计**：不做操作日志/审计留痕。
- **权限体系细化**：仅有学校管理员一个角色，不做菜单级/按钮级权限。

## 3. 术语表

| 术语 | 定义 |
| --- | --- |
| 租户 | 一套独立部署的使用单位（如一所学校）。当前为"单租户运行、多租户就绪"，默认业务租户固定为 `1L`。 |
| 机构 | 消费发生地，分餐厅、档口、超市三类，以树形组织，最多 3 层。 |
| 档口 | 机构类型之一，**必须为叶子节点**，其下不允许再建子机构。 |
| 钱包 | 用户资金的载体，以**手工填写的编号**标识，编号取值 **1~8**。 |
| 工作钱包 | 日常消费的主钱包，消费时优先扣减该钱包。 |
| 追扣钱包 | 与工作钱包成对配置的钱包；当工作钱包余额不足且机构允许追扣时，继续扣减该钱包。 |
| 钱包配对 | 租户级配置：一条 `工作钱包编号 ↔ 追扣钱包编号` 的对应关系。 |
| 机构支付参数 | 机构级的支付行为配置：是否可追扣、使用哪个工作钱包、是否启用身份限制、是否允许脱机消费。 |
| 身份 | 消费主体类别（如学生、老师），在平台内创建维护，扁平一层。 |
| 机构可消费身份 | 某机构允许消费的身份集合（多选）。 |
| 脱机消费 | 设备在离线状态下允许消费；需机构与身份**同时允许**才生效。 |
| 设备 | 部署在机构下的消费终端，以序列号唯一标识。 |
| 下发表 | 由平台根据配置自动生成的「设备 × 交易身份 × 钱包」配置数据集，供设备侧使用。 |
| 有效标记 | 下发表行的状态标记：有效 / 无效。历史行永久保留，仅做标记翻转。 |
| 版本号 | 下发表**租户级批次号**：同一租户内一次配置变更（重算）产生一个新号，从 1 开始递增，本次变更新增的行共用该号；用于标识下发数据的新旧。 |

## 5. 业务概念模型

### 5.1 租户钱包配对（F-1）

租户级维护一张**成对**的钱包配置表，每条记录定义一个「工作钱包 ↔ 追扣钱包」组合：

| 序号 | 工作钱包 | 追扣钱包 |
| --- | --- | --- |
| 1 | 1 | 2 |
| 2 | 3 | 4 |

- 编号由管理员**手工填写数字**，取值 **1~8**。
- 编号即钱包的身份，在整个配对表内**全局唯一**：1~8 中任一数字在「工作钱包」列与「追扣钱包」列合计**最多出现一次**。
- 同一条记录内，工作钱包编号与追扣钱包编号**不能相同**。
- 机构只需指定**一个工作钱包**，对应的追扣钱包由配对表**隐式得出**（例：机构工作钱包 = 1 → 追扣钱包 = 2）。
- 配对**允许删除**，删除后其占用的编号被释放、可再次使用。
- 删除配对**不会**改动引用它的机构支付参数：机构的工作钱包**仍然有效**，只是该机构不再具备追扣能力（无对应追扣钱包），其下发表中的**追扣钱包行随之置为无效**，**工作钱包行保持有效**。
- **修改配对**导致工作钱包编号变化时，引用旧编号的机构支付参数会**级联**把工作钱包改为新编号（旧编号已从配对表消失，不改就会悬空），随后下发表整体重算，工作钱包行与追扣钱包行一并换到新编号。
- 修改配对时若工作钱包编号**未变**、仅追扣钱包编号变化，则机构支付参数不动，只有追扣钱包行换号（工作钱包行保持有效且版本号不变）。

### 5.2 机构树（F-2）

- 树形结构，**无学校/总部根节点**，顶层机构即树的根。
- **最多 3 层**（含顶层）。
- 机构类型：**餐厅 / 档口 / 超市**，类型与层级**不绑定**，管理员可自由选择层级与类型的组合。
- 约束：**类型为「档口」的机构不能有子机构**。
- 餐厅/超市**可以没有档口子节点**（允许直接作为叶子节点存在并挂载设备）。
- 机构创建后：**只能改名**；不允许删除、不允许停用、不允许改类型、不允许变更上级机构。
- 机构名称在**同一父机构下唯一**。

### 5.3 机构支付参数（F-3）

每个机构**独立配置**一份（不继承父机构）：

| 配置项 | 说明 |
| --- | --- |
| 是否可追扣 | 布尔标志。控制设备在工作钱包余额不足时能否继续扣减追扣钱包。 |
| 工作钱包 | **必填，且只能选 1 个**；取值范围为租户钱包配对表中出现的「工作钱包编号」。选定后追扣钱包由配对表隐式得出。 |
| 身份限制 | 布尔开关。**关闭** → 该机构所有身份均可消费；**开启** → 仅「机构可消费身份」列表内的身份可消费。 |
| 可消费身份 | 从身份字典中**多选**（开关关闭时该列表被忽略）。 |
| 是否允许脱机消费 | 布尔标志。 |

### 5.4 身份（F-4）

- 在平台内**创建**维护，扁平一层（无分组、无层级）。
- 字段：身份名称 + 是否允许脱机消费。
- 身份名称在**租户内唯一**。
- 支持**改名**与**删除**，**不支持停用**。
- 身份被删除后，其下发表数据按行级 diff 规则**置为无效**（不物理删除），并变更版本号。

### 5.5 设备（F-5）

- 设备**归属于某一个机构**，归属关系**创建后不可变更**。
- 字段：设备序列号（**全局唯一**）、设备类型（`POS机` / `多媒体人脸机` / `其他`）、归属机构。
- 支持**删除**，删除时**连带删除**该设备的下发表数据。
- 无启用/停用状态。

### 5.6 下发表（F-6）

下发表是「配置态」数据快照，一行代表一个可下发单元：

```
行 = 设备 × 交易身份 × 钱包
```

- **工作钱包行与追扣钱包行始终都下发**，与机构「是否可追扣」**无关**（两者解耦）；机构是否允许追扣只体现在行上的 `是否允许追扣` 字段。
- 机构参数（是否允许追扣、是否允许脱机消费）与钱包信息**各自独立**，同时写入每一行。
- 变更采用**行级 diff**：不原地修改，而是旧行置为无效 + 新增有效行；**失效行永久保留**，并保留其被下发时使用的批次号。
- 版本号为**租户级批次号**：一次配置变更（重算）产生一个新号，本次新增的行共用该号；无实际变更的重算不占用新号。

## 7. 业务规则

| 编号 | 规则 |
| --- | --- |
| BR-1 | 钱包编号由管理员手工填写，取值必须在 **1~8** 之间。 |
| BR-2 | 钱包编号在租户钱包配对表内**全局唯一**：「工作钱包」列与「追扣钱包」列合计，任一编号最多出现一次。 |
| BR-3 | 同一条钱包配对记录内，工作钱包编号与追扣钱包编号不能相同。 |
| BR-4 | 每个机构支付参数必须且只能设置 **1 个工作钱包**，其取值范围限定为租户钱包配对表中已配置的工作钱包编号。 |
| BR-5 | 机构的追扣钱包由「机构工作钱包 + 租户钱包配对表」**隐式推导**得出，不单独配置。 |
| BR-6 | 机构树深度不得超过 **3 层**（含顶层机构）。 |
| BR-7 | 类型为「档口」的机构**禁止**拥有子机构。 |
| BR-8 | 机构名称在**同一父机构下唯一**；身份名称在**租户内唯一**；设备序列号**全局唯一**。 |
| BR-9 | 机构创建后**只允许改名**，禁止删除、停用、改类型、变更上级。 |
| BR-10 | 设备归属机构**不可变更**。 |
| BR-11 | 身份限制开关**关闭**时，该机构所有身份均可消费；**开启**时，仅「机构可消费身份」列表内的身份可消费。 |
| BR-12 | 下发表行的 `是否允许脱机消费` = **机构允许脱机消费 AND 身份允许脱机消费**（机构不允许则一律为否）。 |
| BR-13 | 下发表行 `是否允许追扣` 取自**该设备所属机构**的「是否可追扣」，同一设备下所有行取值一致。 |
| BR-14 | 每个设备下的每个可消费身份，**必须同时下发工作钱包行与追扣钱包行**，且与机构是否可追扣**无关**。 |
| BR-15 | 下发表变更一律采用**行级 diff**：配置新增 → 插入有效行；配置消失 → 原行**原地置为无效**（不改写版本号）；钱包编号变化 → 原行置为无效 + 插入新行。 |
| BR-16 | 下发表**失效行永久保留**，不得物理删除（设备删除导致的连带删除除外）。 |
| BR-17 | 下发表版本号为**租户级批次号**：一次配置变更（重算）在租户内取「当前最大号 + 1」（首次为 1）；本次变更新增的行共用该号，未受影响的行版本号与有效标记均不变。 |
| BR-18 | 关联配置发生变动时，系统必须重新计算受影响行的下发表数据并分配新的批次版本号；重算后无实际变更时不分配新号。 |
| BR-19 | 钱包配对**允许删除**，删除后其编号被释放；删除后引用该配对工作钱包的机构支付参数**保持不变**（工作钱包仍有效），但该机构的追扣钱包行在下发表中**置为无效**，该机构**不再具备追扣能力**。 |
| BR-20 | 身份**允许删除**；删除后该身份的全部下发表行**置为无效**（保留原批次号）。 |
| BR-21 | 失效行保留其被下发时使用的批次版本号，不因失效而改写。 |
| BR-22 | 设备侧契约：新增行的版本号必定大于租户内任何已有行的版本号，设备可用「版本号 > 本地」判断存在新数据；**失效不产生新版本号**，设备必须按自身维度做全量比对，并以 `valid_flag` 识别已失效的行。 |
| BR-23 | **修改配对**导致工作钱包编号变化时，引用旧编号的机构支付参数必须**级联**将工作钱包改为新编号后再重算下发表（旧编号已从配对表消失，否则机构工作钱包悬空、违反 BR-4）；工作钱包编号未变化时机构参数一律不动。 |

**触发下发表重算的配置变动（BR-18 的范围）**

| 变动 | 影响范围 |
| --- | --- |
| 租户钱包设置（新增/修改/删除配对） | 引用该配对的机构下的全部设备；删除配对时其**追扣钱包行置为无效**、**工作钱包行保持有效**；修改配对导致工作钱包编号变化时，引用旧编号的机构支付参数**级联改为新编号**后再重算 |
| 机构支付参数（是否可追扣 / 工作钱包 / 身份限制 / 可消费身份 / 脱机消费） | 该机构下的全部设备 |
| 身份新增/改名/删除、身份脱机参数变更 | 涉及该身份的全部下发行（删除身份时该身份全部行置为无效） |
| 设备新增 | 该设备 |
| 设备删除 | 该设备（连带删除其下发表数据） |
| 机构新增 | 无（尚未配置支付参数时不产生下发数据） |

## 8. 数据模型

> 表名遵循单数蛇形命名；主键为系统内部 ID（雪花算法）；所有业务表含 `tenant_id BIGINT NOT NULL`，不设数据库默认值。物理表结构与 Liquibase 脚本在实现阶段产出。

| 表 | 说明 | 关键字段 | 关键约束 |
| --- | --- | --- | --- |
| `wallet_pair` | 租户钱包配对 | `work_wallet_no`、`deduct_wallet_no` | `(tenant_id, work_wallet_no)` 唯一、`(tenant_id, deduct_wallet_no)` 唯一；编号范围与跨列全局唯一由应用层校验 |
| `organization` | 机构 | `name`、`org_type`、`parent_id` | `(tenant_id, parent_id, name)` 唯一；树深与档口叶子约束由应用层校验 |

## 9. 下发表生成与版本号机制

### 9.1 生成算法

```
对每个设备 D：
  机构 O ← D.organization_id
  参数 P ← O 的机构支付参数      // 未配置则跳过（不生成下发数据）
  身份集合 S ←
      P.身份限制 = 关闭 ? 租户全部身份 : P.可消费身份列表
  工作钱包 W  ← P.工作钱包编号
  追扣钱包 W' ← 租户钱包配对表中 W 对应的追扣钱包编号   // 配对已被删除时记为「无」
  对每个身份 I ∈ S：
      计算目标行集合 T = {
          (D, I, 工作钱包, W,  可追扣 = P.是否可追扣, 可脱机 = P.允许脱机 AND I.允许脱机)
      }
      若 W' 存在，则向 T 追加：
          (D, I, 追扣钱包, W', 可追扣 = P.是否可追扣, 可脱机 = P.允许脱机 AND I.允许脱机)
      用 T 与当前有效行做 diff，按 9.2 落库
```

### 9.2 变更 diff 规则

| 场景 | 以前有 | 本次有 | 处理 |
| --- | --- | --- | --- |
| 新增 | 否 | 是 | 插入 1 条有效行，版本号 = 本次批次号 |
| 消失（如钱包配对被删除、身份被删除） | 是 | 否 | 原行**原地置为无效**，版本号保持原值 |
| 内容变化（如追扣钱包换号） | 是 | 是（钱包不同） | 原行**原地置为无效**（版本号保持原值）；插入 1 条新有效行，版本号 = 本次批次号 |
| 未变化 | 是 | 是 | 不做任何处理（版本号与有效标记均不变） |

### 9.3 版本号规则

- 整数，**租户级**：同一租户内所有下发行共用一个递增序列，从 `1` 开始。
- 分配时机：一次重算若确实产生变更（有新增行或失效行），才占用一个新号 = 当前租户最大版本号 + 1；无变更的重算不占用号。
- 归属：本次重算新增的行统一使用该批次号；被置为无效的行保留其被下发时的批次号，不做改写。
- 单调性：失效行永久保留且保留原号，因此「当前最大号 + 1」必然大于租户内任何已有行的版本号。
- 失效行永久保留，通过 `valid_flag` 与 `version` 表达历史轨迹。
- **设备侧契约**：新增行的版本号一定大于设备本地已有行的版本号，设备可用「版本号 > 本地」判断有新数据；**失效不会产生新版本号**，设备必须按自身维度做全量比对，并以 `valid_flag` 识别已失效的行（见 BR-22）。
